# Hands Diff v2 implementation reference

This is the primary implementation reference for Hands Diff v2. It supersedes
[`v2-draft2.md`](v2-draft2.md) where they differ, while
[`v2-draft1.md`](v2-draft1.md) remains useful background on the original
product direction.

v2 is a macOS-first, post-game League of Legends review experience. The player
focuses on the match; Hands Diff collects a privacy-scoped local session in the
background and provides analysis only after the match.

## 1. Product boundaries

### Primary user and experience

The primary v2 user is a League player reviewing their own games on the web.
The website is post-game only: do not build a live browser dashboard or issue
in-game browser notifications. OBS presentation remains valuable, but input
analysis widgets are disabled by default and must not distract the player.

The initial supported environment is macOS, a single-display setup, and
Summoner's Rift ranked or normal games. Unsupported queues, maps, or invalid
game state must not produce a tracked session.

### Clean-break policy

Hands Diff is pre-release with no active users or production data to preserve.
v2 may replace all previous report schemas, local-session files, database
tables, API routes, plugin settings, sources, fixtures, and renderers. Do not
write importers, dual readers, compatibility shims, or legacy UI. Remove
superseded code and fixtures as part of the relevant change.

A v2 plugin and v2 web service must agree on one current contract. During
development, a version mismatch must fail clearly with an upgrade/rebuild
message rather than attempting to interpret older data.

### Privacy and data handling

Capture events only while League is the frontmost application and only for an
active, supported game. The following never leave the computer: arbitrary raw
keypresses, typed chat text, clipboard contents, application/window titles,
desktop coordinates, and input observed outside a tracked game.

Bound gameplay keys are resolved locally from League's `input.ini`; their
literal configured chords may be shown in OBS. Uploads contain derived,
gameplay-only aggregate data, not a raw key-event stream. This permits a
player to disable the key filter in an overlay without expanding the upload
privacy boundary.

## 2. User-visible behavior

### Session and retention

1. Detect a supported League game and create a session at game time `0:00`.
2. Track input only while League is frontmost. Pausing or changing focus must
   not manufacture events or time.
3. Finalize after the game, calculate derived metrics, and retain the session
   locally.
4. Retain at most 20 completed sessions. On completing session 21, delete the
   oldest session, whether or not it was uploaded.
5. If **Upload game data** is enabled, upload after finalization and retry all
   retained sessions that lack a confirmed upload after each completed game.

**Upload game data** is enabled by default because it is core to v2. When it
is disabled, sessions remain in the local set of 20 until the user enables
upload or they are evicted by a newer session. The UI must make this retention
and deletion behavior clear.

### Quiet tracking indication

Provide an optional small OBS/status indication that a match is being tracked.
It may state the current state (`Waiting for game`, `Tracking`, `Finalizing`,
`Uploaded`, `Waiting to upload`, or `Needs attention`). It must not create a
live web dashboard, browser notification, or in-game gameplay prompt.

### Post-game metrics (initial release)

The recap's initial input summary is deliberately narrow:

- total left clicks, total right clicks, and total clicks;
- total gameplay-bound key actions;
- peak and median APM; and
- peak and median mouse velocity.

Do not make causal claims about these values and game outcomes. Event-linked
insights may follow after real-session testing validates them.

## 3. Capture model

### States

```text
idle → detecting → tracking → finalizing → retained
                 ↘ discarded
```

- **idle:** no session exists and no input is retained.
- **detecting:** confirm a supported Live Client game, identify the active
  player, and establish game time. Do not retain global input.
- **tracking:** begins at in-game `0:00`; capture eligible events only when
  League is frontmost.
- **finalizing:** stop capture, calculate local aggregates, enqueue upload if
  enabled, and request post-game reconciliation.
- **retained:** the completed session occupies one of the 20 local slots.
- **discarded:** incomplete, unsupported, or invalid session; delete it.

Use a monotonic local clock for ordering and duration. Save synchronization
anchors of `(local_monotonic_ms, game_time_ms)` from Live Client observations;
derive each event's `game_time_ms` from the latest anchor. Wall-clock time is
used only to form a match-reconciliation window, never as gameplay time.

### Local event records

The local event stream is the only source of overlay state and input metrics.
Every event has a strictly increasing `sequence`, `local_monotonic_ms`,
derived `game_time_ms`, normalized game-frame pointer position where relevant,
and an input kind.

```json
{
  "session_id": "uuid",
  "sequence": 1842,
  "local_monotonic_ms": 483920,
  "game_time_ms": 321650,
  "pointer": { "x": 0.5274, "y": 0.8431 },
  "kind": "mouse_button",
  "button": "left"
}
```

Pointer coordinates are normalized to the League game frame, never the whole
desktop, using the conversion defined in the
[League HUD layout contract](../hd-obs/docs/league-of-legends-layout.md).
Drop out-of-frame pointer events rather than clamping them.

Store local key events in a separate local-only detail stream. A matched
gameplay key event includes the resolved action ID and configured binding, for
example `spell_1` / `Q` or `self_cast_spell_1` / `Alt+Q`. An unbound literal
key event is eligible only for local overlay display and is never uploaded or
included in post-game metrics.

### Measurement definitions

Evaluate intensity at each one-second game-time boundary using the inclusive
trailing interval `(t - 3 seconds, t]`:

| Measure | Definition |
| --- | --- |
| Total L/R clicks | Count all respective physical mouse-button presses while League is frontmost during tracking. |
| Total clicks | Total left clicks plus total right clicks. |
| Total keys | Count resolved gameplay-bound key actions only. |
| APM | Eligible actions in the trailing three seconds × 20. Eligible actions are left/right clicks plus resolved gameplay-bound key actions. |
| Mouse velocity | Pointer distance in the trailing three seconds ÷ 3 seconds, using valid in-frame pointer-motion samples. |
| Peak | Largest one-second evaluation value in the session. |
| Median | Median of all one-second evaluation values in the session. |

Do not include middle click, arbitrary literal keys, menu browsing, or
unresolved bindings in initial APM/KPM calculations. Preserve enough local
detail to add optional metrics later without changing the capture model.

## 4. League binding resolution

### Settings files

Find `input.ini` alongside the selected `game.cfg`; they are sibling files in
the League configuration directory. The settings UI's existing game-config
discovery/select flow must validate both files, report whether each was found,
and reload the binding map when `input.ini` changes. A manually selected
`game.cfg` selects its sibling `input.ini`; do not scan unrelated files.

Read binding declarations only. Do not persist the full config file, log raw
contents, or claim a binding was found when it is `[<Unbound>]` or blank.

The supplied [`raw-data/input.ini`](raw-data/input.ini) is the parser fixture.
It demonstrates primary, self-cast, normal-cast, smart-cast, modifier, multiple
binding, and champion-specific forms.

### Initial action registry

Resolve at least these `GameEvents` actions and every valid chord configured
for each:

| Player-facing action | `input.ini` keys |
| --- | --- |
| Ability 1–4 | `evtCastSpell1`–`evtCastSpell4` |
| Summoner spell 1–2 | `evtCastAvatarSpell1`–`evtCastAvatarSpell2` |
| Item slot 1–6 | `evtUseItem1`–`evtUseItem6` |
| Trinket / vision item | `evtUseVisionItem` |
| Role-bound / role quest | `evtCastRoleBound` |
| Recall | `evtUseItem7` |
| Shop | `evtOpenShop` |

Also resolve valid self-cast and normal-cast variants for the registry above:
`evtSelfCast*`, `evtNormalCast*`, and applicable `evtSmartCast*` declarations.
Treat a chord as one action when its final non-modifier key is pressed with all
required modifiers down. Do not increment once for the modifier and again for
the chord.

Champion sections such as `[GameEvents.LeeSin]` override a general
`[GameEvents]` binding for that champion. If a binding maps to multiple actions,
record the most specific action and retain its action ID for diagnostics.

### Overlay key filters

Live Keys and Top Keys each have **Show bound keys only**, enabled by default.

- When enabled, show only resolved bindings and their exact chords, such as
  `Q`, `Shift+Q`, `Alt+Q`, or `Cmd+Left Arrow`.
- When disabled, also show literal keys observed while League is frontmost,
  preserving the existing overlay behavior.
- The disabled state affects local display only. Unbound literal keys do not
  enter upload payloads, post-game totals, APM, or Top Keys rankings.

## 5. Plugin source and layout

v2 provides one League source with all related presentation and tracking
settings. It must be useful immediately after adding it: map cover and camera
features are available while input analysis is disabled by default.

The source never manages OBS scene items. It renders within its configured
game-frame canvas; the user chooses any camera source and keeps that source
above the Hands Diff source in the OBS scene.

### General settings

- Map cover: enabled by default; bundled image by default and optional custom
  image picker.
- Camera helper: enabled by default; camera-source selector and existing
  transform controls.
- Camera position: `Next to minimap` or `Opposite of minimap`.
- Automatic game/client switching plus selected game and client captures.
- Advanced game-frame offset, with detected `game.cfg` resolution displayed.
- Game configuration discovery/selection, including sibling `input.ini` status.

### Safe-area camera anchors

Continue using the normalized, game-frame safe-area behavior in the
[League HUD layout contract](../hd-obs/docs/league-of-legends-layout.md),
including minimap flipping and single-display offset handling.

- **Next to minimap:** anchors to the minimap's inner edge and expands toward
  the central HUD.
- **Opposite of minimap:** anchors between the central HUD and the opposite
  screen edge.
- Both anchors use 100% of their available safe-area width. Width must not be
  reduced merely to preserve a preferred camera size.
- Both have a maximum height of 200% of the minimap height. The camera source
  may letterbox/crop inside that rectangle according to the selected transform.

### Input analysis settings

Input analysis is disabled by default. Enabling it exposes upload state,
tracking status, the local key-filter controls, and independent top/left/right
HUD layouts. Widget configuration is local presentation only; the web recap
does not depend on it.

Initial widget registry:

| Widget | Areas | Notes |
| --- | --- | --- |
| Cumulative totals | top, left, right | L/R clicks, clicks, or gameplay-bound keys. |
| Live key row | top, left, right | Includes **Show bound keys only**. |
| Mouse distance | top, left, right | Local overlay value. |
| Input intensity | top, left, right | Uses the three-second rolling window. |
| Mouse activity map | left, right | Current pointer and qualifying local trail. |
| Top keys | left, right | Includes **Show bound keys only**. |

Retire dwell-time hexbin presentation. The activity map shows the current
pointer and a newest-first trail of the latest 20 qualifying events. Older
trail entries are 5% less opaque than the next newer entry. Left/right/middle
clicks are red/blue/yellow; key labels are shown only when permitted by the
local key filter.

## 6. Riot and Live Client integration

### During the game

Use Live Client Data for current game context, identity display values, and
time synchronization. Poll at a bounded documented cadence (initially once per
second), recording changes instead of repeated identical objects.

Relevant fixtures are [`raw-data/activeplayer.json`](raw-data/activeplayer.json)
and [`raw-data/allgamedata.json`](raw-data/allgamedata.json). At session start,
persist the captured values:

- `riotIdGameName` and `riotIdTagLine` from Active Player;
- game time, map number/name, and game mode from All Game Data; and
- a local wall-clock start observation for later bounded reconciliation.

The current fixtures do not supply a PUUID or a Match-V5 match ID. Do not
assume either is present in Live Client Data and do not attempt to resolve the
match until the session completes.

### After the game

The web service, never the plugin, owns the Riot API key and performs this
reconciliation sequence:

1. Resolve the captured-at-start Riot ID with Account-V1:
   `/riot/account/v1/accounts/by-riot-id/{gameName}/{tagLine}`.
2. Confirm the returned PUUID is the same as the PUUID for the user's linked
   Hands Diff account. On mismatch, leave the report unattached and show a
   reconciliation error; do not guess.
3. Request candidate Match-V5 IDs with
   `/lol/match/v5/matches/by-puuid/{puuid}/ids`.
4. Fetch candidate match records and select one whose start time is within the
   session's narrow time window and whose participant, map, queue, and mode
   agree with the local session.
5. Persist the verified `metadata.matchId` and `info.gameId`, then fetch the
   corresponding timeline.

Match-V5 is the post-game authority. Use the
[match reference](match-v5.md) for final result, participant, economy, rune,
and team data; use the [timeline reference](match-v5-timeline.md) for exact
event timestamps and periodic state. Join the resolved PUUID to the timeline
participant ID. Align input events to timeline events using each event's own
`timestamp`, never the enclosing frame's timestamp.

If reconciliation is delayed or fails, deliver an input-only recap with an
explicit status and retry path. When it later succeeds, enrich the existing
report; do not create a duplicate recap.

## 7. Upload and web contract

The plugin sends one current v2 report schema only. The service rejects prior
versions rather than migrating them. Submission is idempotent on
`(account, report_id, payload_hash)`.

The upload includes:

```text
report ID and schema/capture-policy versions
captured-at-start Riot ID, observed game-start window, map/mode details
input aggregates and one-second derived intensity series
gameplay-bound action counts and capture/truncation/completeness flags
compact Live Client state changes needed for future recap context
reconciliation and upload status
```

The payload excludes arbitrary literal keys and raw local event streams. The
service validates ownership, schema, payload size, time-bucket ordering, and
the absence of disallowed raw-key fields before accepting it.

The first recap has a match header, the defined input summary, a clearly marked
data-completeness/reconciliation status, and final Match-V5 results once
available. It may show a timeline for navigation, but linking input patterns to
kills, deaths, objectives, purchases, or level-ups is deferred until it has
been validated against real tracked games.

## 8. Required tests and acceptance criteria

### Capture and storage

- No session input exists before game time `0:00`, after finalization, or while
  League is not frontmost.
- A session at game time `0:00` is tracked even if leaving-base rules change.
- Session 21 deletes the oldest retained session, uploaded or not.
- Enabling upload retries every retained unconfirmed session after a completed
  game; disabling it performs no automatic upload.
- Three-second evaluation fixtures verify APM and velocity at boundaries, peak,
  and median calculations.

### Binding and privacy

- The fixture resolves primary, modifier, multiple, unbound, and
  champion-specific bindings correctly.
- A modifier chord produces exactly one resolved action.
- Bound-only overlay display excludes unrelated keys; disabling it shows an
  unrelated frontmost literal key locally.
- Arbitrary literal key data cannot appear in an upload or alter post-game
  totals/APM.
- `evtUseItem7` resolves as Recall for the initial supported mapping.

### Layout and reconciliation

- Both camera anchors respect the safe area for either minimap side, consume
  the available width, and cap at twice minimap height.
- Offset game frames use normalized game-frame coordinates, not desktop
  coordinates.
- The supplied Live Client fixtures provide captured Riot ID and game context;
  Account-V1 returns a PUUID; Match-V5 candidates are verified by the stated
  time/context checks.
- A PUUID mismatch, missing Match-V5 match, or failed upload leaves one
  retryable report with clear status and no duplicate recap.
- Timeline alignment uses `event.timestamp`, not a frame timestamp.
